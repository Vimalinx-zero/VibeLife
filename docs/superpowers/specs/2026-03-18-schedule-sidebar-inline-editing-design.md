# Schedule Sidebar Inline Editing Design

**Date:** 2026-03-18

## Context

日历页右侧栏已经收成了 `当天安排 / 今日待办` 两个标签，但这两块仍然停留在“浏览态优先”的层次：

- `今日待办` 只能勾选、删除和新增，想改文案还要去别处处理；
- `当天安排` 只能查看，右栏里已经能新增，但不能直接改已有条目；
- 用户现在明确要求“点一下之后就可以直接进入编辑”。

这意味着右侧栏不应只是展示区，而要成为一个可直接操作的工作区。

## Goal

把日历页右侧两块核心内容改成“单击即原地编辑”：

1. 在 `今日待办` 中，点任务文本即可原地编辑任务内容；
2. 在 `当天安排` 中，点事件卡片即可切换成原地编辑卡片；
3. 保存后立刻写回后端；
4. 取消时恢复原展示态，不污染别的卡片；
5. 不破坏现有标签切换、日期切换、局部刷新和手动添加行为。

## Non-Goals

- 这一轮不改右侧栏整体布局。
- 不新增新的后端接口，只复用已有更新接口。
- 不引入弹窗编辑器或全屏编辑器。
- 不改左侧月历交互。
- 不处理批量编辑、多选编辑或拖拽排序。

## User-Approved Scope

用户已确认采用“原地 inline 编辑”而不是弹层：

- `今日待办`：点内容直接变输入框；
- `当天安排`：点卡片直接进入编辑；
- 保持当前页面结构，不额外跳转。

## Approaches Considered

### Approach A: 原地 inline 编辑

Pros:
- 点击路径最短，和用户要求完全一致；
- 保持当前页工作流，不需要新的弹层状态；
- 与现有 `TodoList` 的编辑模式一致，容易复用交互习惯。

Cons:
- 需要在右栏里处理更细的局部编辑状态；
- 当事件卡片字段较多时，卡片高度会暂时变高。

### Approach B: 点击后弹小编辑卡片

Pros:
- 状态集中，编辑表单更好排版；
- 不会让列表项局部变形。

Cons:
- 比原地编辑多一层交互；
- 和用户已明确表达的“点一下直接进编辑”不一致。

### Approach C: 侧边统一编辑器

Pros:
- 编辑体验完整，便于未来扩展更多字段。

Cons:
- 会再次挤占右栏高度；
- 与当前右栏标签式布局方向相反；
- 明显超出本轮所需。

## Decision

选择 **Approach A: 原地 inline 编辑**。

这是最贴合现有右栏结构和用户预期的方案。它只增加局部编辑状态，不改变页面骨架，也能直接复用已有更新 API。

## Design

### 1. 今日待办：单项文本原地编辑

`今日待办` 每条任务保持现有的勾选和删除按钮。变化点只有中间内容区：

- 默认展示文本；
- 点击文本区后，该项切换为编辑态；
- 编辑态显示单行输入框，以及保存 / 取消两个小按钮；
- `Enter` 保存，`Escape` 取消；
- 保存时调用 `updateTodo(id, { text })`；
- 保存成功后刷新待办列表，并退出编辑态；
- 保存失败时保留编辑态和当前输入，避免用户内容丢失。

约束：

- 同一时刻只允许一个待办处于编辑态；
- 点击 checkbox 或删除按钮时，不进入编辑；
- 已完成任务也允许改文案，但仍保持完成样式语义不变。

### 2. 当天安排：整张卡片原地编辑

`当天安排` 中每张事件卡片默认仍显示标题、时间、说明和类型点。

点击卡片主体后，该卡片切换为编辑态：

- 标题：单行输入框，必填；
- 时间：单行输入框，可空；
- 说明：多行文本框，可空；
- 类型：下拉框，可改 `meeting / deadline / reminder / task`；
- 底部显示保存 / 取消操作。

保存时调用 `updateScheduleEvent(event.id, payload)`。

更新成功后：

- 退出编辑态；
- 以最新数据刷新当前月份事件；
- 顶部日期和当前标签保持不变。

更新失败时：

- 保持当前编辑态和输入内容；
- 弹出错误提示；
- 不清空当前列表。

### 3. 编辑状态边界

这轮只做“局部单项编辑”，避免多项并发编辑带来的复杂度。

具体约束：

- `今日待办` 同时只允许一个 todo 处于编辑态；
- `当天安排` 同时只允许一个事件卡片处于编辑态；
- 切换标签时，未保存编辑直接退出；
- 切换日期时，未保存编辑直接退出；
- 刷新后若数据重载，旧编辑态不保留。

这是更稳妥的边界：右栏当前已有日期切换和标签切换，若还要保留悬挂草稿，会让状态明显变复杂。

### 4. 刷新与数据同步

保存成功后不只更新本地文本，而是走统一的数据同步路径：

- `今日待办`：保存成功后重新拉取待办列表；
- `当天安排`：保存成功后重新拉取当前月份事件；
- 若需要通知其他区域同步，继续复用现有 workbench refresh 事件；
- 右侧当前 tab、当前选中日期不因刷新而重置。

### 5. 视觉与可点击范围

原展示态下：

- `今日待办` 的文本区应显示为可编辑热点，但不额外引入夸张装饰；
- `当天安排` 卡片整个内容区都可点击进入编辑，避免只点标题才生效。

编辑态下：

- 输入区背景保持实体，不透明；
- 保存 / 取消按钮需要可点击且不会被 hover 容器遮住；
- 编辑内容仍在原滚动区内，不创建新的浮层。

## Data Flow

### 今日待办编辑

1. 用户点击任务文本；
2. 本地记录 `editingTodoId` 与当前文本草稿；
3. 用户编辑并保存；
4. 前端调用 `updateTodo`；
5. 成功后重新加载今日待办并清空编辑态；
6. 失败时保留当前草稿并提示错误。

### 当天安排编辑

1. 用户点击某张事件卡片；
2. 本地记录 `editingEventId` 和该事件的编辑草稿；
3. 用户编辑并保存；
4. 前端调用 `updateScheduleEvent`；
5. 成功后重新加载当月日程并清空编辑态；
6. 失败时保留当前草稿并提示错误。

## Error Handling

- 任务文本为空时，不提交，并给出提示。
- 事件标题为空时，不提交，并给出提示。
- 更新接口失败时，不退出编辑态，不清空用户输入。
- 日期切换、标签切换和外部刷新发生时，直接丢弃未保存编辑态，不尝试自动合并。

## Testing Strategy

由于当前仓库没有现成的 React DOM 组件测试栈，这轮测试分两层：

1. 把编辑状态与草稿整理逻辑提成纯函数，使用 `node:test` 做 TDD；
2. 再通过前端类型检查、构建和手工页面验证确认真实点击交互。

重点验证：

1. `今日待办` 编辑 helper 能正确进入编辑、规范化文本、取消编辑；
2. `当天安排` 编辑 helper 能正确创建草稿、拒绝空标题、构造更新 payload；
3. `tsc` 和 `build` 继续通过；
4. 手工验证点击 todo 文本立即进入编辑；
5. 手工验证点击事件卡片立即进入编辑；
6. 保存、取消、切换 tab、切换日期都不会把右栏交互打坏。
